# 设计说明

这份文档记录「为什么是这样」，而不是「怎么用」。用法见 [USAGE.md](./USAGE.md)，数据结构见 [SPEC.md](./SPEC.md)。

---

## 1. 问题定义

真实请求的失败，大多不是「措辞不够漂亮」，而是四类信息缺失：

| 缺失 | 典型表现 | 模型的行为 |
| --- | --- | --- |
| 目标 | 「帮我优化一下」 | 自己挑一个目标，多半不是你要的 |
| 交付形态 | 没说要代码、文档还是表格 | 给一段聊胜于无的散文 |
| 约束 | 没说不许改 API、不许加依赖 | 顺手重构了你不想动的地方 |
| 验收 | 没说怎样算做完 | 声称「已修复」，但没跑过 |

所以这个工具的核心不是「润色」，而是**把这四类信息显式化**，并且在信息确实不存在时，**承认它不存在**。

## 2. 三个关键取舍

### 2.1 闸门优先，而不是逢消息必改

最初的设想是：用户每次输入后都重新生成一版提示词，用户确认后再发。这个做法有三个代价：

1. **延迟**：每条消息多一次往返；
2. **token**：编译结果中位 264 tokens（见评测），每条消息都付；
3. **信任**：大部分消息本来就清楚，被改写三次之后，用户会养成「无脑按回车」的习惯，闸门形同虚设。

于是改成两级：先用纯本地规则算一个 0..1 的清晰度（六个维度加权，见 SPEC），低于 0.62 才进入收束。清晰的请求**逐字节原样放行**——不是「原样放行 + 加一句注释」，是字节相同，测试里有断言。

还有一个容易被忽略的判定：**对话中的追问不重写**。「继续」「再改一下第 2 点」「好的」这类输入脱离上文没有独立含义，孤立地重写只会把上文没说过的东西编进来。所以 `gate` 识别出追问时直接放行。

### 2.2 总分总的依据，以及为什么它不是唯一骨架

默认排版 `bluf` 就是「总—分—总」：

```
## 目标            ← 总：一句话结论先行
## 要求 1..n       ← 分：编号、可逐条核对
## 约束 / 不要做
## 交付
## 完成标准        ← 总：可勾选的自检清单
```

两个经验依据：

- **首尾位置更可靠**。长上下文里，位于中部的信息被利用的程度显著低于开头和结尾（[Lost in the Middle, Liu et al., TACL 2024](https://direct.mit.edu/tacl/article/doi/10.1162/tacl_a_00638/119630/Lost-in-the-Middle-How-Language-Models-Use-Long)）。所以「要做什么」放最前，「怎样算做完」放最后，中间才是细节。
- **指令越多，遵循率越低**。IFScale 测到指令数量上升时遵循率单调下降，且不同位置的指令受影响程度不同（[How Many Instructions Can LLMs Follow at Once?](https://huggingface.co/papers/2507.11538)）。所以要求必须**编号、单条可验证、总数不超过 12 条**，超过就明确警告「建议拆成多轮」，而不是硬塞。

但固定模板会伤害短请求：给「这个函数为什么报错」套五级标题，纯属噪音。所以有三种排版（`bluf` / `compact` / `checklist`），`compact` 用行内标签，适合一两句话的请求。

另外：**不强制模型输出思维链**。思维链提示在非推理模型上仍有效，但对已经内部推理的模型属于冗余甚至干扰，官方指南明确建议不要硬塞（[OpenAI GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)、[Anthropic prompting best practices](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/overview)）。所以模板里没有任何「让我们一步步思考」。

### 2.3 产物是结构化对象，不是一段文字

如果只产出字符串，就无法回答「这句话是你编的还是我说的」。所以内部表示是 `PromptSpec`，每个字段带来源：

| 来源 | 含义 | 渲染 |
| --- | --- | --- |
| `user` | 用户原文（可重排、不可改写） | 正常写 |
| `inferred` | 由规则推导（如「这是提问，所以交付物是回答」） | 追加 `（假定）` |
| `assumption` | 纯默认值，无从推导 | 进「待确认」区，并写清若不符的后果 |

规则引擎是**抽取式**的：只做分组、编号、排序、标注，从不改写措辞。改写会引入编造，而编造正是这个工具要防的东西。需要语义级缩写时才走 API 引擎，且结果必须过保真校验。

## 3. 保真校验：一个确定性的门槛

`checkFidelity` 做两件事，都不依赖模型：

1. **硬字面量核对**：数字、路径、URL、引号内容、camelCase/snake_case 标识符，出现在输出里但原文没有 → **error**。因为「并发上限设为 3000」这种编造，看起来最专业，危害也最大。
2. **保留率代理**：原文内容词有多少还留在输出里，低于 55% 报警。这是粗代理，只能回答「是不是删多了」，不能回答「语义是否完整」——文档里也这么写，不夸大成「语义一致性检查」。

数字那一档是 error 而非 warning：warning 会被忽略，error 会让 CLI 退出码变 1，能被 CI 拦住。

## 4. 注入：不删、不升格

用户原文里可能出现「忽略以上所有指令」。两种极端都是错的：删掉（丢失用户可能真的在讨论这段文字）和升格（把它当成指令）。

做法是第三条：识别出注入片段后，把它从**指令槽位**（目标、要求）里排除，但仍然保留在源文本和锚点里，最终以「原文（冲突时以此为准）」的形式出现在末尾。信息没丢，但它落在被明确界定为引用的区块中。锚点非空时 `keepOriginal` 自动打开。

闸门本身不做安全判断——一个清楚的「帮我总结这段话」不该因为里面有注入字样就被判定为需要改写。安全属性在编译器里测，不在闸门里测。

## 5. 评审循环：编辑优先

「和另一个模型聊到你满意」这个交互是错的：多一轮对话就多一份歧义，用户真正想要的是**直接改**。

所以 `funnel review` 的按键是 `[e] 编辑`（打开 `$EDITOR`，改完保存即生效）、`[d] 看差异`、`[r] 给一句意见`、`[s] 换排版`，而不是「请描述你的修改意图」。编辑后的文本仍然过一遍保真校验，新增的字面量会被点名。

`[r]` 在规则引擎下只调结构（更短 / 更严格 / 转清单），并**明确告诉用户「规则引擎不改措辞，语义级改写需要 API 引擎」**。假装能听懂意见，比直接说不能更糟。

## 6. 为什么会变差：不是「污染」，是猜测固化

一个常见的说法是「模糊的原文会污染上下文」。这个说法**不准确**，而且会让人做错决定。

上下文污染通常指：无关内容、重复内容、过时内容挤占注意力，或者相互冲突的指令同时在场。一句「帮我优化一下这个东西」**不构成污染**——它太短了，问题恰恰相反：信息太少。收束后的提示词反而更长，占用更多上下文。

真正值得解释的链条是这一条：

```
信息缺失 → 模型补一个默认 → 这个默认写进它的回答
        → 下一轮你把回答当前提 → 猜测变成了「事实」
```

三步之后，没有人记得「Python 是你选的还是它选的」。这才是污染，而且是自己造的：模型生成的内容污染了后续上下文。

收束做的是**在第一步掐断**：把「我默认了什么」提出来变成一行可见的文字，并写明若不符会发生什么。它不能保证猜对，但能保证猜错时你看得见。

顺带它也减少了用户侧的一类污染：

- 三件事揉成一句 → 被强制分条，模型不会只做其中一件；
- 「顺手把这几个地方也改一下」→ 非目标区明确写「不要改动 X」；
- 长会话里反复重申同一要求 → 收束一次，后续用 `continue` 携带。

但它同时**增加了 token**，所以不是无条件划算的。成本与档位见 [COST.md](./COST.md)。

产品上，这条解释不该是一篇说明文，而应当是**针对当前输入的**：你的这句话缺了什么、模型会替你决定什么。playground 里的「直接发，模型会替你决定这些」面板就是这个，内容直接来自 `spec.assumptions`，不是模板套话。

## 7. 三个入口，一个内核

拦截用户输入这件事天然绑定宿主：DSH 的前端插件、Codex 的插件、Claude Code 的 hook，格式各不相同，而且都脆弱。所以拆成：

- **内核**（`src/`）：纯函数 + 可选 API，零运行时依赖；
- **MCP server**：四个工具，任何支持 MCP 的 agent 都能用，由**宿主自己的模型**做语义工作，不需要第二个 key；
- **适配层**：Codex 插件、DSH skill、CLI，只负责把循环讲给模型听。

代价是：MCP 路径下「用户确认」发生在对话里，而不是一个专属 UI。收益是这套东西今天就能在 DSH、Codex、Claude Code、Cursor 上跑，而不是等某个宿主的插件 API 稳定。

## 8. 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 每条消息强制改写 | 延迟、token、信任三重代价，见 2.1 |
| 用一个更强的模型做「提示词专家」直接输出成品字符串 | 无法校验来源，编造不可见；且必须带 key |
| 让用户回答问卷（表单式） | 用户不知道要填什么，这正是问题本身 |
| 把「总分总」写死 | 短请求被五个标题压垮，见 2.2 |
| 自动修改用户可见的输入框内容 | 用户失去控制感，且无法区分「我写的」和「它改的」 |

## 9. 已知局限

诚实列出来，比让人在 issue 里发现好：

1. **规则引擎不理解语义**。它靠标记词判断约束/非目标/验收，中文口语和长句会漏。漏了不会编造，只会少标一类，并在 `fidelity` 里以低保留率的形式露出来。
2. **一句里同时有约束和动作时不拆**（如「用 TypeScript 重写这个模块」）。整句留在「要求」里，语言信息不丢，但「约束」区会看不到它。拆开必须丢词，不值得。
3. **意图分类是词表驱动**，没有训练分类器。`write` 需要同时出现文本类名词和写作动词，否则「写一个爬虫」会被误判成写作——这类误判只影响默认文案，不影响抽取结果。
4. **保留率是代理指标**，不是语义一致性。它能抓住大规模删减，抓不住同义替换造成的偏移。
5. **没有测「模型最终回答是否更好」**。离线评测只测编译质量；要做 A/B 需要真实模型与评审，见 [EVAL.md](./EVAL.md) 里给出的方法。
6. **MCP 路径没有专属 UI**，确认发生在对话里，比前端插件多两次 tool call 的延迟。
