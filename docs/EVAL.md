# 评测

## 现在测什么

`evals/` 里有 16 条手工标注的真实请求，覆盖：清晰提问、清晰指令、追问、模糊单句、多目标、编号列表、带代码块、英文、写作、排障、约束密集、长段落、注入、乱码、计划。

评测完全不联网、不需要 key，可以进 CI：

```bash
npm run eval                 # 跑，打表格
node evals/run.mjs --write-report   # 同时生成 report.md
```

### 指标

| 指标 | 定义 | 为什么用它 |
| --- | --- | --- |
| 闸门一致率 | 判定与人工标注一致的比例 | 闸门是这个工具信任度的上限：不该改的改了，用户就关掉它 |
| 保真率 | 原文内容词在输出中的保留比例（中位数） | 抓「编译时把关键信息删没了」 |
| 未溯源字面量 | 输出中出现、原文中没有的数字/路径/URL/标识符 | 抓编造。这是 error 而不是 warning |
| 长度 | 原文 token → 输出 token（中位数） | 收束有代价，必须量化 |
| 结构 | 要求条数、问题个数 | 问题和要求都有一个「多了就没人看」的上限 |

### 当前结果

见 [report.md](../evals/report.md)。最近一次：

```
cases            16
passing          16/16
gate agreement   100%
passed through   5
median retention 100%
tokens           raw 18 → compiled 264 (median)
invented tokens  0
```

怎么读这几个数：

- **16/16** 说明规则与标注一致，不说明模型回答变好了。
- **raw 18 → compiled 264 tokens**：每条被收束的请求，中位开销约 250 tokens。这是真实成本，写在这里而不是藏起来。
- **0 未溯源字面量**：编译器没有凭空造数字。这是它敢动用户提示词的前提。

## 没测什么

**没有测「模型最终回答是否更好」。** 这是这个项目最重要的缺口，没测的原因很实际：需要真实模型、多轮采样、人工或评审模型打分，成本和噪声都不小，不适合放在默认流程里。

补上的方法（欢迎提 PR）：

1. **对照组**：`raw`（原文直发）/ `compiled`（收束后）/ `compiled+answers`（把用户对问题的回答也并进去）。
2. **模型**：至少两个不同家族，各 3 次采样，temperature 固定。
3. **评审**：先人工，再考虑模型评审。人工用 5 分钟一条的盲评，评四件事——
   - 是否命中用户真实意图（1–5）
   - 是否遵守了约束（是/否，逐条）
   - 是否编造了事实（有/无，逐条列出）
   - 需要几轮返工才能可用（0/1/2+）
4. **报告**：给出均值与置信区间。样本小于 30 条时不要写「显著提升」。

预期结论大概率是**分场景**的：多目标任务、缺验收的任务会明显变好；单点提问没差别甚至更差（多了 250 tokens 和一层结构）。README 里应该照实写分段结论，而不是一个总平均。

## 为什么不做自动 LLM-as-judge 断言

1. **不稳定**：同一个 judge 在同一批样本上会翻转，`npm test` 会随机红。
2. **可被讨好**：judge 看到「结构化、分点、有验收清单」的提示词，容易给高分——它评的是形式，不是结果。
3. **掩盖问题**：一个漂亮的平均分，会让人不去看那几条真实翻车的用例。

所以默认评测只做**确定性、可复现**的部分；模型侧评测作为独立脚本和人工报告存在，不阻塞 CI。

## 加一条用例

编辑 `evals/dataset.json`：

```json
{
  "id": "my-case",
  "tag": "compile",
  "raw": "用户的原始输入",
  "expect": {
    "decision": "compile",
    "must_keep": ["必须原样保留的字面量"],
    "min_requirements": 2,
    "must_ask": true,
    "force": false
  },
  "note": "这条用例想验证什么"
}
```

`decision` 写的是**你希望的行为**，不是当前代码的行为。用例失败时，先判断是代码错了还是期望错了——两者都要在 PR 里说清楚。
