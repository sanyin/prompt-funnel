# 提示词收束（prompt-funnel）

你的任务不是把用户的话写得更好看，而是**把缺失的信息显式化**，并且**在信息确实不存在时承认它不存在**。

## 什么时候用

用：

- 一句话里有多件事（「写个爬虫，加个代理池，再做个面板」）
- 只说目标不说形态（「优化一下这个」）
- 没有验收标准，但明显是要交付东西
- 用户明说「帮我整理成提示词」「我要发给别的模型」

不用：

- 明确的单点提问（「这个报错为什么」）→ 直接回答
- 追问（「继续」「再改第 2 点」）→ 脱离上文重写会编造
- 闲聊、确认、致谢

判断不准时，先调用 `funnel_gate`，它会给出判定和理由；`pass` 就别改，直接回答。

## 循环

1. **`funnel_analyze`**：传入用户原文（逐字，不要自己先改写）。
2. **把 review 摘要给用户看**：目标、要求条数、默认假设、建议的问题。问题**最多 3 个**，且只问会改变方案的那种（受众、交付形态、范围、验收方式）。不要问能猜到的。
3. **等用户回复**。用户可能会：改某个字段、说「就这样」、或回答其中几个问题。
4. **改 spec**：只改用户明确说了的部分。其余保持原样。**不得新增原文没有的事实**——不补技术栈、不补数字、不补文件名。
5. **`funnel_render`**：传回 spec **和 `source`**（原文）。它会做保真校验。
6. **看校验结果**：如果报了「未溯源字面量」，先问用户那些数字/路径对不对，再发送。
7. **把返回的 prompt 作为本轮发给模型的内容**。

## 硬规则

- **不编造**。任何用户没说过的事实，只能进 `assumptions`（并写清若不符的后果）或 `openQuestions`。
- **原文优先**。用户的原话在冲突时是权威；`keepOriginal` 会自动把原文附在末尾。
- **不替用户做决定**。范围、受众、技术栈这类选择，问一次；用户不答就按默认假设走，并在输出里标明是假设。
- **用户说「就这样 / 直接发 / 别改了」时立刻停**，不要再来一轮。
- **一次只收束一次**。已经收束过的内容不要再套一层模板。

## 没有 MCP 时

如果这个环境没有 `funnel_*` 工具，用 CLI 代替：

```bash
# 拿判定（0 成本，不调模型）
funnel gate "<原文>" --json

# 拿结构化结果
funnel compile "<原文>" --json        # 输出 spec，可读可改
funnel compile "<原文>"               # 输出最终提示词
```

CLI 不存在时，退化成手工执行本文件的规则：把原文拆成「目标 / 要求（编号）/ 约束 / 不要做 / 交付 / 完成标准」，缺的部分写进「待确认」，并明确标出哪些是你补的假设。
